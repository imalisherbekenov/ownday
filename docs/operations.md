# Эксплуатация Ownday

## Перед выпуском

Нужны отдельные production/staging базы и секреты. SESSION_SECRET обязателен; веб и бот должны использовать согласованные настройки. Для production-бота обязательны HTTPS WEBHOOK_URL и TELEGRAM_WEBHOOK_SECRET. Миграции выполняются только через prisma migrate deploy после проверки на копии данных. prisma db push, migrate reset и пересоздание production исключены.

Публикация веба выполняется после резервной копии и репетиции миграций production-базы. Android APK и AAB подписаны отдельным ключом выпуска; iOS собран для симулятора. Проверки на физических устройствах и выпуск в магазины ещё не выполнены. Новый мобильный клиент требует новой серверной версии /api/sync. Точные результаты сборок приведены в mobile-release.md и implementation-progress.md.

## Репетиция восстановления

Остановить записи в отдельную тестовую БД. Указать TEST_DATABASE_URL на localhost и имя, начинающееся с ownday_test. Установить клиентские pg_dump/pg_restore той же или совместимой версии PostgreSQL; при необходимости указать PG_BIN.

```sh
pnpm db:verify-backup
pnpm db:verify-backup --with-fixture
```

Скрипт создаёт custom-format архив, восстанавливает его в новую временную БД и сверяет количество и контрольную сумму всех строк каждой таблицы. Флаг --with-fixture добавляет искусственного пользователя с привычкой и дробной отметкой, затем удаляет только этого пользователя. Скрипт удаляет только созданную им БД с проверенным случайным именем. Архив и отчёт остаются в игнорируемом .test-postgres/backups. Скрипт намеренно не принимает DATABASE_URL и не работает с удалённой/production БД.

Для production нужны резервные копии вне основного сервера, ограниченные права доступа, установленный срок хранения и регулярная проверка восстановления в отдельном окружении. Результат локальной репетиции не подтверждает восстановимость производственных копий. Перед переносом реальных данных определить RPO/RTO и проверить сохранность аккаунтов, UUID, истории, сессий и миграций.

## Наблюдение

Следить за частотой 401/429/5xx, временем /api/sync, числом и возрастом pending/failed ReminderDelivery, истечением аренды, ошибками миграций и доступностью БД. Содержимое привычек, email, коды входа, токены и полные тела запросов не отправлять в журналы/аналитику. Сейчас отдельный сервис мониторинга и оповещения не подключён.

API синхронизации и обмена мобильного/Apple входа пишет JSON-события в стандартный журнал среды: event, requestId, status, durationMs, at. Заголовок x-request-id связывает ответ с записью. Тела запросов, идентификаторы пользователей, адреса и тексты исключений в эти события не включаются. События требуют настроенного приёмника и правил оповещения в выбранной среде; сами по себе они не уведомляют владельца.

GET /api/health доступен только с Authorization: Bearer и отдельным OPS_HEALTH_TOKEN длиной не менее 32 символов. Проверяет соединение с БД и возвращает количество окончательно неуспешных доставок и возраст самой старой ожидающей доставки. Ограничения: ожидание транзакции 1 секунда, SQL 1,5 секунды, транзакция 2,5 секунды. Ответ 200 означает доступность БД, а не успешность всех внешних доставок. Проверять queue.failed > 0 и рост queue.oldestPendingSeconds отдельными правилами. Публичные страницы не раскрывают состояние очереди.

Для staging сначала проверить неправильный токен (401), отключённую БД (503), нормальное состояние (200) и искусственную просроченную доставку. Не подключать оповещения, отправляющие данные в сторонний сервис, до настройки этого сервиса владельцем.

Историю операций и tombstone нельзя удалять только по возрасту: старое офлайн-устройство может повторить операцию. Сначала нужен протокол минимально поддерживаемой версии/срока синхронизации. Продуктовая аналитика и сторонний сбор ошибок пока не включены.

AccountDeletionReceipt хранит только хэши сессии/идентификатора и срок действия подтверждения удаления, без истории и контактных данных. Повторное подтверждение поддерживается семь дней. После expiresAt запись можно удалять отдельной задачей обслуживания; до настройки такой задачи физическое удаление просроченных подтверждений не автоматизировано. Для AuthGrant также требуется удаление просроченных записей. Пользовательские журналы синхронизации этим правилом не затрагиваются.
